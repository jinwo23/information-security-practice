# Звіт аудиту безпеки — Електронний деканат

## 1. Резюме

Було проведено комплексний аудит безпеки REST API «Електронний деканат». Перевірялися механізми автентифікації, авторизації, захисту даних, валідації введення, аудиту, моніторингу, Docker hardening, HTTPS та DevSecOps-перевірки.

За результатами аудиту система має кілька рівнів захисту: JWT-автентифікацію, RBAC, хешування паролів, шифрування персональних даних, audit log, rate limiting, HTTPS через Nginx, non-root Docker-контейнер, security headers та автоматичні перевірки безпеки.

Основні ризики, які залишаються: відсутність MFA, відсутність WAF, частковий захист від CSRF, використання self-signed сертифіката для локальної розробки.

## 2. Реалізовані шари захисту Defense in Depth

| Шар | Механізм | Практична |
|---|---|---|
| 1. Інфраструктура | Docker Compose, SQLAlchemy ORM, Alembic | №2–3 |
| 2. Автентифікація | Bcrypt-хешування паролів, JWT access/refresh tokens | №4–5 |
| 3. Авторизація | RBAC з ролями admin, teacher, student | №5 |
| 4. Валідація вводу | Pydantic-схеми, bleach-санітизація, CSP, Rate Limiting | №6 |
| 5. Шифрування даних | Fernet AES для персональних даних, зашифровані backup-файли | №7 |
| 6. Аудит і моніторинг | audit_log за правилом 5W, brute force detection, security stats | №8 |
| 7. Безпека середовища | Docker non-root, HTTPS через Nginx, Trivy, Bandit, pip-audit | №9 |

## 3. Модель загроз STRIDE

| STRIDE | Загроза для деканату | Реалізований контрзахід | Бажаний контрзахід |
|---|---|---|---|
| Spoofing — підробка | Підробка JWT-токена | JWT з HMAC-SHA256 підписом | RS256 + token blacklist |
| Tampering — зміна даних | Підміна оцінки через API | Pydantic-валідація + RBAC | MFA для зміни оцінок |
| Repudiation — заперечення | Викладач заперечує зміну оцінки | Audit Log з правилом 5W | Цифрові підписи логів |
| Information Disclosure — витік даних | Читання email або телефону з БД | Field-Level Encryption | Шифрування всієї БД |
| Denial of Service — відмова в обслуговуванні | Перевантаження API запитами | Rate Limiting, Nginx | Cloudflare WAF |
| Elevation of Privilege — підвищення привілеїв | Студент отримує права admin | RBAC require_role() | ABAC + granular permissions |

## 4. Матриця ризиків

| Загроза | Ймовірність | Вплив | Ризик | Рівень | Статус захисту |
|---|---:|---:|---:|---|---|
| Brute Force | 4 | 3 | 12 | Високий | Rate Limiting + Brute Force Detection |
| SQL Injection | 2 | 5 | 10 | Високий | ORM + Pydantic-валідація |
| XSS Stored | 3 | 4 | 12 | Високий | Санітизація + CSP |
| JWT Token Theft | 2 | 5 | 10 | Високий | Частково, бажано HttpOnly Cookie |
| Витік файлу БД | 2 | 5 | 10 | Високий | Field-Level Encryption |
| CSRF | 3 | 3 | 9 | Середній | Частково, CORS без CSRF-токенів |
| DDoS | 3 | 3 | 9 | Середній | Частково, Rate Limiting |
| Соціальна інженерія | 4 | 4 | 16 | Критичний | Потрібні MFA та навчання користувачів |

## 5. Результати тестування

| Тест | Результат | HTTP Code | Висновок |
|---|---|---:|---|
| Доступ без токена | Очікується блокування доступу | 401 | Захищений ендпоінт не має відкриватися без JWT |
| IDOR — доступ до даних іншого студента | Перевіряється обмеження доступу до чужих даних | 403/404 | Студент має бачити лише свої дані |
| Вертикальна ескалація student > admin | Очікується заборона | 403 | RBAC має блокувати доступ |
| XSS script tag | Очікується відхилення або санітизація | 400/422 | Введення має проходити фільтрацію |
| SQL Injection OR 1=1 | Очікується помилка або порожній результат | 400/422 | ORM не має виконувати ін?єкцію |
| SQL Injection DROP TABLE | Очікується відхилення | 400/422 | Структура БД не має змінюватися |
| Brute Force 10+ спроб | Очікується обмеження частоти | 429 | Rate Limiting має спрацювати |
| Security Headers | Заголовки присутні | 200 | HSTS, X-Frame-Options, nosniff працюють |

## 6. Знайдені вразливості та рекомендації

| Проблема | Рівень | Рекомендація |
|---|---|---|
| Немає MFA для адміністратора | Високий | Додати MFA для admin та teacher |
| Self-signed сертифікат | Середній | Для production використовувати Let’s Encrypt |
| Частковий CSRF-захист | Середній | Додати CSRF-токени або SameSite HttpOnly cookies |
| Немає WAF | Середній | Додати Cloudflare або інший WAF |
| Trivy знаходить вразливості без доступного fixed version | Середній | Регулярно оновлювати базовий образ і залежності |
| Немає SIEM | Низький | У production інтегрувати централізований збір логів |

## 7. Висновок

Система «Електронний деканат» має базову ешелоновану систему захисту. Реалізовано автентифікацію, авторизацію, шифрування персональних даних, захист від SQL Injection, XSS, brute force, аудит дій користувачів, HTTPS та Docker hardening.

Загальна оцінка стану безпеки: достатній рівень для навчального проєкту. Для production потрібно додати MFA, WAF, повноцінний SIEM, production TLS-сертифікат, регулярний dependency scanning у CI/CD та додаткове penetration testing.
